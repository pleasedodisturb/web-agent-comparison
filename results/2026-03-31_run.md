# Web Agent Comparison Report — 2026-03-31

## Executive Summary

Five web automation agents were tested against real job application flows on Anthropic's Greenhouse board and Replit's Ashby board. **Playwright MCP dominates** (9.07/10) with the richest tool surface and batch form filling. **WebFetch** is the surprise #2 for read-only tasks. **Agent Browser CLI** is a strong alternative for scripted automation outside Claude Code. **Lightpanda** is fast but fatally limited by its JS engine. **BrowserMCP** disconnected mid-test — connection instability is its defining weakness.

## Deep Analysis by Agent

### 1. Playwright MCP — 9.07/10 (Winner)

**Integration:** MCP server (28 tools), clean Chromium instance

**Key Strengths:**
- `browser_fill_form` is a game-changer — fills multiple fields in ONE tool call (6 fields at once vs 4+ commands for others)
- Richest tool surface: evaluate, network intercept, drag, file upload, console messages
- Warm browser means fast navigation (~2-3s per page)
- Accessibility snapshots are structured and token-efficient
- Full JS/React rendering — Ashby SPA rendered perfectly

**Key Weaknesses:**
- React Select comboboxes (common in Greenhouse) aren't native `<select>` elements — `browser_select_option` fails, requiring `browser_run_code` fallback
- No auth/cookies — can't access gated content (LinkedIn profiles, internal tools)
- Chromium process memory overhead (~200-400MB)

**Verdict:** The clear winner for application automation. `browser_fill_form` alone justifies using it over alternatives. Only use something else when you need auth (BrowserMCP) or just need to read a page (WebFetch).

### 2. WebFetch — 7.87/10 (Best Read-Only)

**Integration:** Built-in Claude Code tool, zero setup

**Key Strengths:**
- Zero setup — always available, no configuration
- AI-summarized output — ~1.5KB of structured text vs 16-33KB raw
- Highest token efficiency by far
- Reliable on server-rendered pages (Greenhouse worked perfectly)
- 15-minute cache for repeated access

**Key Weaknesses:**
- Read-only — cannot interact with pages at all
- Failed on Lever careers page (CSS-only response — Lever requires JS rendering)
- No JS rendering — depends on server-side HTML
- Cannot fill forms, click buttons, or upload files

**Surprise finding:** WebFetch extracted Ashby/Replit data successfully despite Ashby being a React SPA. This suggests Ashby may have server-side rendering (SSR) or the WebFetch model handles partial HTML well.

**Verdict:** Use first for any "read and extract" task. Fastest, cheapest, most token-efficient. Switch to Playwright only when you need interaction.

### 3. Agent Browser CLI — 7.60/10 (Best CLI Alternative)

**Integration:** Standalone Rust CLI (`agent-browser` v0.23.4), Chromium-backed

**Key Strengths:**
- Full Chromium rendering — Ashby React SPA rendered perfectly
- Complete interaction surface: open, click, fill, upload, screenshot
- Scriptable from Bash — works outside Claude Code sessions
- Snapshot format nearly identical to Playwright's accessibility tree
- Rich command set: drag, hover, focus, check, evaluate, PDF export

**Key Weaknesses:**
- **Cold start is brutal: 25-40 seconds** for first `open` command (Chromium launch)
- No batch fill — one `fill` command per field (4+ commands vs Playwright's 1)
- Ref format quirks: bare `e3` works, `@ref=e3` doesn't; upload needs CSS selectors, not refs
- Each command is a separate process (no persistent session management out of the box)

**API Inconsistency Found:**
- `fill` accepts bare refs (`e3`) ✓
- `click` accepts bare refs (`e3`) ✓
- `upload` rejects refs, needs CSS selectors (`input[type="file"]`) ✓/✗
- This is likely a bug or design oversight

**Verdict:** Best choice for CI/CD pipelines or scripted automation outside Claude Code. The cold start penalty makes it unsuitable for interactive use, but great for batch operations.

### 4. Lightpanda CLI — 5.87/10 (Fastest, Most Limited)

**Integration:** Standalone Zig binary (`lightpanda` at `~/.local/bin/`, 59MB)

**Key Strengths:**
- **Blazing fast:** 1.5-1.8 seconds per page (vs 25-40s for Agent Browser)
- Tiny binary (59MB vs Chromium's ~400MB)
- Three output modes: markdown (cleanest), semantic_tree (structured), semantic_tree_text
- Has MCP mode (`lightpanda mcp`) for potential Claude Code integration
- Has CDP server mode for programmatic control

**Key Weaknesses:**
- **Fatal: Cannot render React/SPA pages** — returned 0 bytes for Ashby
- Read-only in fetch mode (no interaction)
- No form filling, no clicking, no file upload
- Zig-based JS engine is fundamentally limited compared to V8

**The 0-byte Problem:**
Lightpanda's Zig JS engine cannot execute the React JavaScript that Ashby uses to render job postings. The page HTML is an empty shell with a `<div id="root">` — all content is injected by JavaScript. Lightpanda downloads the HTML, attempts JS execution, and fails silently, producing no output.

**Verdict:** Only viable for high-volume scraping of traditional server-rendered pages. The JS limitation is a dealbreaker for modern SPA-based job boards (Ashby, Lever, Workday). Has untested MCP mode that could make it useful as a fast alternative to Playwright for simple pages.

### 5. BrowserMCP — 5.53/10 (Unreliable, Niche)

**Integration:** MCP server connecting to user's real Chrome/Brave via extension

**Key Strengths (Theoretical):**
- Access to authenticated pages (LinkedIn, YNAB, internal tools)
- User's real cookies and sessions
- Full Chrome JS engine
- Accessibility snapshots same format as Playwright

**Key Weaknesses (Observed):**
- **Disconnected mid-session** — connection between Chrome extension and MCP server dropped without warning
- Requires manual user action: open tab → click "Connect" on extension
- Only 12 tools (vs Playwright's 28) — no `evaluate`, no `file_upload`, no `network_requests`
- Shares browser with user — automation can interfere with their work
- Privacy concern: page content goes to Anthropic's API

**Why It Scored Lowest:**
The fundamental issue is reliability. BrowserMCP depends on a Chrome extension maintaining a WebSocket connection to a local MCP server. This connection dropped during our test, rendering all planned stages untested. For a tool whose primary value is "access to authenticated content," being unavailable when you need it defeats the purpose.

**Verdict:** Only use when you absolutely need authenticated access (LinkedIn profiles, internal dashboards). Never rely on it for automated workflows — have a fallback plan.

## Decision Framework

```
Need to extract data from a public page?
  └─→ WebFetch (zero setup, AI-summarized, fastest)

Need to interact with a page (fill forms, click, upload)?
  └─→ Playwright MCP (richest tools, batch fill, warm browser)

Need scripted automation outside Claude Code?
  └─→ Agent Browser CLI (full CLI, Chromium-backed)

Need to scrape high volume of simple HTML pages?
  └─→ Lightpanda CLI (1.5s per page, but no SPA support)

Need authenticated/gated content (LinkedIn, internal tools)?
  └─→ BrowserMCP (if it's connected) + Playwright MCP as fallback
```

## Optimal Combo for Job Application Automation

The ideal job application flow combines tools:

1. **WebFetch** → Extract job posting data (read the listing)
2. **Playwright MCP** → Fill application forms (interact with ATS)
3. **BrowserMCP** → LinkedIn-gated content (view profiles, check connections) — with fallback

This 3-tool combo covers the full pipeline: discover → extract → apply.

## Key Findings

### 1. Lever is Now Unreachable
Lever career pages (`jobs.lever.co/*`) returned CSS-only responses to WebFetch and 404 to Playwright. They've either migrated away from this URL structure or added anti-scraping protection. Any Lever-based automation may need updating.

### 2. React Select Dropdowns Are a Universal Problem
Both Playwright MCP and Agent Browser CLI had to work around Greenhouse's React Select comboboxes (not native `<select>`). This is the #1 form-filling gotcha across all agents. Agent Browser handled it better (type + Enter worked cleanly) while Playwright needed `browser_run_code`.

### 3. Background Agents Can't Run CLI Tools
Subagents launched in background mode don't inherit Bash permissions — both Lightpanda and Agent Browser background agents were blocked. CLI-based testing must run in the main session.

### 4. Speed vs Capability Is the Core Tradeoff
| Agent | Speed (first page) | Can interact? | Can render SPA? |
|-------|-------------------|---------------|-----------------|
| WebFetch | ~3s | No | Partial |
| Lightpanda | ~1.8s | No | **No** |
| Playwright MCP | ~3s (warm) | **Yes** | **Yes** |
| Agent Browser | ~40s (cold) | **Yes** | **Yes** |
| BrowserMCP | N/A (disconnected) | Yes | Yes |

### 5. Token Efficiency Varies 20x
| Agent | Output for same page |
|-------|---------------------|
| WebFetch | ~1.5KB (AI-summarized) |
| Lightpanda | ~16KB (raw markdown) |
| Playwright MCP | ~33KB (accessibility tree) |
| Agent Browser | ~28KB (accessibility tree) |

WebFetch is 20x more token-efficient because it uses a small model to summarize. For context-window-constrained workflows, this matters enormously.
